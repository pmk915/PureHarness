# Reproducible CLI demo

This is an **offline scripted demonstration**, not an LLM solving a task or
benchmark performance evidence. The existing `cli.main(model_factory=...)`
injection seam is also used by CLI tests. Only the model responses are scripted;
the unmodified Agent, coding tools, workspace discipline, policy, local command
backend, CLI renderers, durable sessions, RunRecords, and JSONL renderer execute
normally. No production provider or CLI option was added.

The fixed task is deliberately small: read `calculator.py` and `check_add.py`,
replace subtraction with addition through `apply_patch`, run three local checks
with `run_command` explicitly marked `purpose="verification"`, and finish.
It uses a fresh copy of [the fixture](../examples/cli_demo_workspace/) rather
than benchmark machinery. A new invocation is needed for another run: this is
not a general-purpose coding assistant or an autonomous repair demonstration.

## Setup

Run all commands from the repository root. Python 3.11+ and the installed CLI
extra are required for Rich/input editing. Installation may need network access;
the demo itself needs no API key, `.env`, network, Harbor, Docker, external
dataset, or additional recording dependency.

```bash
python -m venv .venv
.venv/bin/python -m pip install -e '.[cli]'
.venv/bin/python examples/cli_demo.py --help
demo_root=$(mktemp -d -t pureharness-demo.XXXXXX)
```

Keep this shell open: later commands reuse `$demo_root`. Every `--output-dir`
must be a **new** directory; existing paths are refused, never reset or deleted.
Omit that flag to create a persistent temporary directory whose path is printed
on stderr. Interactive state is isolated under that directory, not your normal
PureHarness home. The helper does not load credentials. The existing local
backend still inherits the environment and is not a sandbox; use only this
trusted fixture and review recordings for unrelated terminal content.

## Compact interactive flow

Use a real terminal, preferably **110 columns × 32 rows**, with a readable
monospace font. Do not pipe/redirect this command: non-TTY stdout selects plain
presentation rather than Rich. There is no forced-color/rendering hack.

```bash
.venv/bin/python examples/cli_demo.py --output-dir "$demo_root/compact"
```

At the real `You ›` prompt, enter these lines individually:

```text
Fix add in calculator.py and verify it with check_add.py.
/status
/eval
/exit
```

The task must match exactly: the model is a fixed script, not a prompt parser.
Watch the actual read, patch, command, verification, completion, final-response,
and RunRecord-path output. Compact mode emphasizes effects and new outcomes;
it intentionally omits per-request model/context/policy detail. `/eval` is
read-only and does not execute another check. The verification outcome is
generated by the local command, not a fabricated display line.

## Verbose and plain flows

Use a new output directory and the **same input lines** above:

```bash
.venv/bin/python examples/cli_demo.py --verbose --output-dir "$demo_root/verbose"
.venv/bin/python examples/cli_demo.py --plain --output-dir "$demo_root/plain"
```

Run these separately, exiting each before the next. On a TTY, `--verbose`
shows context building, model requests, policy boundaries, and evidence detail.
`--plain` forces English plain output; redirected output is also plain even if
`--verbose` is supplied. `--plain --verbose` is rejected. Add `--locale zh-CN`
for Chinese Rich presentation; the fixed task and scripted answer remain
English. Plain rendering is not localized.

## Machine-readable flow and evidence

This separate invocation forwards the task to the existing `run --output jsonl`
path. It is not a recording of the earlier interactive run.

```bash
.venv/bin/python examples/cli_demo.py --jsonl --output-dir "$demo_root/machine"
.venv/bin/pureharness inspect "$demo_root/machine/run.json"
.venv/bin/pureharness inspect "$demo_root/machine/run.json" --json
```

JSONL-only stdout is also saved verbatim to `machine/events.jsonl`. Setup
instructions/diagnostics go to stderr, and failures keep a nonzero exit code.
Interactive presentation flags are rejected with `--jsonl` in this example.

| Artifact | Location under `$demo_root` | Meaning |
|---|---|---|
| Modified workspace | `<mode>/workspace/calculator.py` | Real copied fixture edited by the tool |
| Interactive RunRecord | `<mode>/records/<run_id>.json` | Finalized per-run evidence; CLI prints the exact path |
| Durable interactive session | `<mode>/state/sessions/<session_id>.jsonl` | Raw Session and associated RunRecords |
| Machine RunRecord | `machine/run.json` | Finalized evidence from the separate one-shot run |
| Live events | `machine/events.jsonl` | Actual versioned JSONL events, including coding/progress snapshots |

Inspect an interactive record with `pureharness inspect` using the path printed
by the CLI. Mutation and verification counters are live coding evidence, not
new RunRecord fields. For example, read them without running any tool:

```bash
.venv/bin/python - "$demo_root/machine/events.jsonl" <<'PY'
import json
import sys
from pathlib import Path

events = [json.loads(line) for line in Path(sys.argv[1]).read_text().splitlines()]
coding = [event for event in events if event["event"] == "coding_evidence_snapshot"]
print(json.dumps(coding[-1]["payload"], indent=2, sort_keys=True))
PY
```

For an unmodified fixture, the expected trajectory has five model requests,
four tools, one structured mutation, one marked verification attempt with exit
zero, and `end_reason="completed"`. These are reproducible behavioral checks,
not a universal quality score or external success claim. Run IDs, session IDs,
timestamps, absolute workspace/interpreter paths, durations, and token estimates
may differ; do not expect byte-identical evidence or terminal recordings.
No fixed success output is printed by the model: its final answer directs you
to the observed verification outcome. If a tool errors or verification fails,
the normal failure/recheck lifecycle remains in effect; the example cannot
repair an unexpected state or serve another task.

## Real capture instructions

No screenshot or GIF has been captured or committed yet. The
[asset directory](assets/README.md) tracks the intended files and review rules.
Capture the **actual terminal**; never reconstruct UI text, substitute outcomes,
or describe a scripted-model capture as a real-model benchmark.

For compact/verbose screenshots, execute the respective command above, submit
the task, then capture the terminal with your OS screenshot tool after the
RunRecord path appears. A taller terminal or a second verbose screenshot may
be needed; do not crop away the scripted-demo disclosure. `/eval` can be a
separate frame. Review paths and unrelated terminal content before publication.

On Linux with util-linux `script`, record the real PTY output and timing:

```bash
script -q -e -O "$demo_root/compact.typescript" -T "$demo_root/compact.timing" \
  -c ".venv/bin/python examples/cli_demo.py --output-dir '$demo_root/compact-recording'"
script -q -e -O "$demo_root/verbose.typescript" -T "$demo_root/verbose.timing" \
  -c ".venv/bin/python examples/cli_demo.py --verbose --output-dir '$demo_root/verbose-recording'"
```

Enter the same input lines in each recording. These files contain real output
and timing, **not images or GIFs**, and stay outside Git. The flags are
util-linux-specific; on other systems use terminal screen recording instead.

Optionally, if `asciinema` and `agg` are already installed, record and convert a
real session to a GIF (neither is a project dependency):

```bash
asciinema rec --cols 110 --rows 32 \
  -c ".venv/bin/python examples/cli_demo.py --output-dir '$demo_root/gif-recording'" \
  "$demo_root/pureharness-demo.cast"
agg "$demo_root/pureharness-demo.cast" "$demo_root/pureharness-demo.gif"
```

Check the locally installed versions' `--help` if their options differ. Keep the
task, effects, disclosure, and record location visible; aim for under one minute
without changing execution or generating synthetic frames. Only after review,
publish genuine assets under `docs/assets/` and embed the compact screenshot in
both READMEs together. No placeholder image link should be added before a real
image exists.
